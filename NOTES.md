# notepad mint

## 1.0.11 default text editor, names from 2026 (2026-10-09)

- asked: "make .txt open with notepad mint by default / add option in windows for extensions"; the maintainer chose installer + an in-app item and the plain text set (.txt .log .ini .cfg .conf .md .csv .nfo .diz .text). windows 8+ protects the default (UserChoice hash): a program can only register itself as a choice and open settings; the last click is the user's.
- installer: component "text file types" (default on) writes, in the 64-bit view on 64-bit windows (`SetRegView 64`: RegisteredApplications in WOW6432Node is not read), a progid `notepad-mint.text` (windows' own text icon `imageres.dll,-102`, `"exe" "%1"`), `Applications\notepad-mint.exe` (FriendlyAppName, SupportedTypes), `OpenWithProgids` per extension (the extension's default is never touched), `Software\notepad mint\Capabilities` + `RegisteredApplications` "notepad-mint", then SHCNE_ASSOCCHANGED. finish page box "choose notepad mint as the default for text files" opens `ms-settings:defaultapps?registeredAppMachine=notepad-mint` (unticked on an update that already had the keys, hidden without the component). the uninstaller deletes only our values (`DeleteRegKey /ifempty` ignores values, so shared keys are left alone), in HKLM and HKCU. the installer itself was compiled, not run here (it needs admin).
- app: help > set as default text editor (`assoc.c`, advapi32 loaded at run time: the exe still imports 3 dlls) writes the same keys under HKCU for the running exe and opens `registeredAppUser=`; an installed copy whose HKLM keys point at this exe only opens `registeredAppMachine=` (one entry in settings). unit test `TestAssoc` redirects HKCU to a throwaway key with `RegOverridePredefKey`. exe 147,968 bytes (+4.6 KB, mostly the key strings).
- names: `DOCNAME_EPOCH` 2026 (asked: "start from 2026 instead"): days since 2026-01-01 with the real leap rules (the 100 year cycle 2026-2125 contains 2100, no leap year: 36,524 days * 45 = 1,643,580 < 36^4); a year before 2026 counts as the end of the cycle. a 1.0.10 counter (~440k) is more than `DOCNAME_AHEAD` ahead of the new clock, so `DocNameNext` resyncs.

## 1.0.10 right to left, sequential untitled names, notepad parity and an audit (2026-10-09)

The maintainer reported "RTL not working at all" (the edit menu item "does nothing"). Driving the item through the real popup path (WM_CONTEXTMENU + its mnemonic) toggled the styles on the private desktop, on the real desktop and with the installed 1.0.9, so the "nothing" was not reproduced; what was found and fixed:

- right aligned text ran into the editor's hidden overhang (`SBAR_TRIM`, 5 px at the right) and was cut off, and the left scrollbar of a right to left editor was full width. the overhang now sits on the side of the vertical bar: `EditArea` (main.c) moves the editor left by the trim, `EditViewRect` (edit.c, also used by edit_caret.c) is the visible part of the client area, `Strips` (sbar.c) trims the left strip when the target has `WS_EX_LEFTSCROLLBAR`. `EditSetRtl` re-pads and re-reveals the caret; main.c `SetRtl` re-runs `Layout`.
- automatic reading order (asked for): `EditStrongDir` takes the first letter with a direction (`GetStringTypeW` CT_CTYPE2, bounded to 4096 units) on open and on every change while the user has not picked an order (`g_dirManual`, cleared by new / open), like `dir="auto"`. file > new starts left to right.
- ctrl+right shift / ctrl+left shift set right to left / left to right (notepad's keys): `g_shiftDir` in `EditProc`, cancelled by any other key, a click, the wheel, alt, and by `Cmd` (an accelerator such as ctrl+shift+n eats the next key: `EditDirKeyCancel`).
- tests: T44 (22 checks: open hebrew / latin / neutral-first files, overhang geometry, the formatting rectangle, typing into an empty document, the menu path, both shortcuts incl. set-not-toggle and a key in between, word wrap re-creation, new).

Untitled names (asked for: "start at 0000 for 2000, only the last two digits of the year, the counter increasing slowly every new document"): `DocNameClock` = days since 2000-01-01 (year mod 100) * 45 + seconds of the day / 1920 (45 steps of exactly 32 minutes a day; a century is 1,643,625 steps < 36^4, so four base-36 characters always, the first one steps every 2.8 years: `9...` in 2026). `DocNameNext` = last + 1 while that is ahead of the clock by at most a year (`DOCNAME_AHEAD`), else the clock (a new century or a clock that was far off re-syncs). `PrefsTakeDocName` keeps the last name in settings.ini `[name] last` under a named mutex, so every new document in every window gets a higher name. side effect: starting the app now writes that one key (T8.0 accepts it).

Audit (five read-only reviewers: notepad parity, document / settings code, editor / find / ui code, rt.asm and hot loops, ux / cleanup; every finding was checked before it was fixed):

- parity: `/a file` and `/w file` (open as ansi / utf-16, `CmdSwitch`), `/p` no longer shows the window first and uses the full path; f1 shown on help topics; a zoom panel (`SB_ZOOM`, empty = no panel at all, so the status text is unchanged at 100%) that resets on a click; a click on the position opens go to line. tests T45 (/a, /w).
- `DocRead` refused a utf-8 file with a bom and one bad byte, and an odd-length utf-16 file, with "no mapping for the unicode character": now `OpenDoc` asks, and `DocAllowLossy(TRUE)` opens it with U+FFFD (the strict default and its unit tests are unchanged). T7.10-10e.
- settings: a window closed later wrote back every key it had loaded (window 1 dark, window 2 switches to light, closing window 1 wrote dark again): `AppSavePrefs` now writes only what this window changed since it read / wrote them (`g_saved`), or a key that is missing. `WM_ENDSESSION` saves; a window closed while minimized from maximized keeps `maximized=1` (`WPF_RESTORETOMAXIMIZED`).
- a recent file that fails to open (locked, the new lossy prompt cancelled) is removed from the list only when it is gone; reopen with encoding asks about unsaved changes before the encoding dialog and is grayed without a file (T7.13-19).
- f5 inside the find dialog's text boxes no longer inserts the time into the document; `Cmd` no longer pulls the focus out of an active find dialog; alt+z (re-created editor) keeps a backwards selection's caret at its start; enter on the about link opens it; right arrow on a submenu leaf moves to the next menu; the scrollbar trim follows a dpi change.
- speed: `wlow` looks non-ascii units up in a 64k table made once with two string-form `CharLowerW` calls (surrogates excluded); case-ignoring search in cyrillic went from 18.4 to 3.3 ms per million units (`tests\bench`, the 1.0.9 per-unit system call kept there as `FindSysLower`). new `mp_find3` (rt.asm, sse2, bounded reads like `mp_count_lf`) jumps a forward search to the next possible first character and `DocRead` from one line break to the next (with run copies in the normalising pass): a miss over 1M units of plain text takes 94 us (the audit measured 640-860 us on 1.0.9's scan). `HashText` runs four independent lanes over 32-bit words. unit tests: `mp_find3` every hit position x lengths 0..40 x 8 alignments x 3 values with byte traps and a protected page; the table against `CharLowerW` for all 65,536 units; the name clock for every day of the century.
- cleanup: `ParseColor` / `FormatColor` / `WildMatch` (leftovers of removed features, used only by their unit tests) and `MenuActive` (unused) removed with their tests.

Not done, offered instead: multi-level undo / redo (the stock edit has one level; a real stack is 4-6 KB and touches every text path), in-place save fallback for folders that refuse new files and for hard links (`ReplaceFileW` replaces the directory entry), external-change reload, ime open / reconversion menu items, dialog mnemonics, a cached bitmap for buffered painting.

## 1.0.9 font sizes: 10 pt default, 6 x 4 preset grid 8 to 48 pt, typed 7 to 100 pt with decimals (2026-10-09)

- sizes are stored in tenths of a point (`g_pf.pt`, `FONT_MIN` 70, `FONT_MAX` 1000, default 100 = 10 pt). the ini key is `size10` (tenths); a settings.ini that only has the old whole-point `size` is read as points and converted.
- the font dialog's size box accepts 7 to 100 pt and one decimal digit ("8.5"); the preset grid is 6 columns by 4 rows, 8 to 48 pt: 8 8.5 9 9.5 10 10.5 / 11.5 12 12.5 13 13.5 14 / 16 18 20 22 24 26 / 28 32 36 40 44 48. bold / italic moved down to make room.
- ctrl+plus / ctrl+minus / ctrl+wheel step along their own ladder, 8 to 48 pt (`g_ladder` in edit.c, tenths); a size typed above 48 pt goes down to 48 on the first ctrl+minus.
- the default is 10 pt (`PrefsDefaults` in prefs.c; an existing settings.ini keeps its saved size).

## decisions / design notes
- edit control = native EDIT (multiline, ES_NOHIDESEL). text kept utf-16 + CRLF inside; DocRead normalises, DocWrite converts.
  word wrap toggle = recreate the edit control (like notepad). colors via WM_CTLCOLOREDIT.
- **selection = windows' default highlight.** an accent overpaint (answering `WM_PAINT` while a selection exists, painting the control into a bitmap via `WM_PRINTCLIENT` and painting the selected runs over it) was built,
  verified with screenshots and then removed on request: it flickered, because the stock control paints a *changed* selection straight onto the window (not through `WM_PAINT`), so every selection change needed a forced repaint.
  (what it needed on the way: the stock highlight is one pixel wider than its text, found by counting `#0078d7` pixels in a screenshot.)
- **selected line breaks** (`edit.c`, section "selected line breaks"; asked for on 2026-10-06: "i can't tell which lines / characters are selected, empty lines show nothing"). the stock control highlights characters only, so a selected CR LF left no trace: an empty line inside a selection looked unselected,
  the end of a selected line looked like the selection stopped there. now every visible row whose *hard* line break is inside the selection gets a block at the end of its text: one space wide (`g_stubW`), one row high, `GetSysColor(COLOR_HIGHLIGHT)` (the colour the control itself uses).
  a soft wrap is no line break: none with word wrap on, none at the control's own split of a line over 1024 characters, none after the last line.
  **how it is drawn**: not by overpainting in `WM_PAINT` with a bitmap (that is what flickered, see above) but straight onto the window with `GetDC`, right after the control has handled a message that can change what it shows (`StubSync`: keys, mouse buttons and drag, the control's timer, cut / paste / clear / undo, the selection and scroll `EM_` messages, size, font; **not** the `EM_` queries, they come by the dozen)
  and after each paint of its own (`WM_PAINT` and `WM_PRINTCLIENT` hooks, so PrintWindow shows the blocks too). the caret is hidden around the drawing (`HideCaret` / `ShowCaret`: it is an inverting caret).
  where the blocks go: `EM_GETSEL`, the control's text buffer read in place (`EM_GETHANDLE`: a row ends in a hard break when CR LF sits right before the next row's start, `EM_LINEINDEX`) and `EM_POSFROMCHAR` of that CR = the end of the row's text. only the rows on screen are looked at: the cost is the number of visible rows, not the document.
  every message goes straight to the stock window proc (`Ctl()`): through `EditProc` each `EM_*` would run `SbarSync`. a block that has to go is not painted over: its spot is invalidated and updated, so the control repaints it itself. that is insurance: measured on windows 11 (build 22631) the control already erases the end of every row it repaints, a probe build with the cleanup switched off passed the same checks.
  measured: the control now and then wipes a block that stays (the start row's, while the selection's *start* moves) a moment before the sync draws it again: same thread, microseconds, not visible. `EM_POSFROMCHAR` packs x into 16 bits, so rows estimated wider than 30000 px (`tmMaxCharWidth` x characters; only at huge zoom) are skipped (their end cannot be scrolled to anyway).
  right to left: the block grows to the left of the row's end when that is at or left of the row's start (rtl text; an empty row in an rtl editor, at the right margin). **known gap**: a left to right line in an rtl editor ends at the margin, its break has no room: no block there.
  tested by `T23`: PrintWindow (shape, one cell wide and one row high, which breaks count, soft vs hard wrap, zoom) and, with a probe build, the window itself (`tools\probe.bat /DSHOTDC`: `WM_APP + 90` dumps the editor's own DC, because PrintWindow repaints through `WM_PAINT` and would hide what the control painted straight onto the window, and a process on another desktop cannot read the DC):
  blocks after `EM_SETSEL`, shrink / grow, only the break leaving the selection, a mouse drag and back, `EM_LINESCROLL`, collapse = gone. `tools\verify.bat ui` runs that probe build too. with the block drawing switched off, 14 of the 23 checks went red.
- **partly visible rows** (`edit.c`, section "partly visible rows"; asked for on 2026-10-06: "we need to partially render text e.g. text not visible below current scroll area", read as: the cut-off row at the bottom of the editor). the stock control draws whole rows only **and rounds its formatting rectangle down to whole rows** (`EM_SETRECTNP` asked for 204 px keeps 200: measured),
  so below the last whole row there was a blank band: the bottom padding plus up to a row of what was left over, and the next row was cut off by blankness instead of by the edge of the editor. now that row (and a second one when the band is tall enough: padding + the leftover can be more than a row) is drawn there, clipped at the bottom edge of the editor.
  `EDIT_BAND_INSET` (`mp.h`) = how far above the edge it stops: 0 = the text runs to the edge (as in other editors), `EDIT_PAD` = the bottom padding stays blank. **not done**: the other reading, virtualised rendering for huge files / an own text view instead of the native edit (TODO item 2): the control still builds its line index for the whole text.
  what the control counts as in view stays the whole rows: page size, scroll ranges and `EM_SCROLLCARET` are the stock ones. a click on the partial row hits that row (`EM_CHARFROMPOS` is not clamped) and the control scrolls it whole, like it did for the blank band.
  **how**: not by widening the formatting rectangle for the paint (tried: the control then draws the partial row itself, perfectly, but every `EM_SETRECTNP` re-wraps the whole text when word wrap is on, 59 ms a call at 1000 lines and 580 ms at 10000, and at the end of the document the control moves the first visible row by one for good). with GDI instead: `TabbedTextOutW` (what the control uses: the same font, the default tab stops, the same language pack for shaped scripts),
  in up to three pieces (before / inside / after the selection), onto a band-sized bitmap, then ONE blit. the control is kept from erasing the band (`WM_ERASEBKGND` with the band excluded from the clip), so there is never a moment with only the background in it. painted after the control's own `WM_PAINT` / `WM_PRINTCLIENT` and, like the line break blocks, right after each message that can change what it shows (`BandSync`, the `StubWatch` list plus the IME messages):
  the control's scrolling moves only the pixels of its formatting rectangle, so the text under the band is not moved by it. the highlight is the control's (`COLOR_HIGHLIGHT` / `COLOR_HIGHLIGHTTEXT`, one pixel wider than the text); a selected hard line break gets the same block as `StubDrawAll`'s, none after the last line. the caret is never in the band (the control hides it for a row it does not count as in view; measured).
  **left blank** (today's look): a right to left editor's band (the control erases it as before); rows of arabic / hebrew *presentation forms* (plain GDI draws them differently from the control: measured); rows with right to left letters or bidi marks **while any of the row is selected** (the highlight in reordered text is not one rectangle to find by measuring); rows wider than the 16 bits a text width has (the limit of the blocks; a tab counts as 8 widest characters).
  everything else was compared pixel for pixel with the control's own row: ascii, tabs, japanese, accented latin / greek / cyrillic, combining marks, emoji, half width katakana, thai, devanagari, arabic and hebrew, word wrap, zoom, both themes, a selection inside / through / over the end of the row, the last line, an empty line, sideways scrolled lines. thai / devanagari text inside a selection is up to one level of one colour channel off (the control draws shaped rows another way).
  tested by `T25`: PrintWindow, scroll one row, and the band's pixel rows must be those of that row drawn whole by the control (the test takes the caret away with `WM_KILLFOCUS`: after the scroll the caret is in a whole row, where it shows); with the probe build also the window itself after `EM_LINESCROLL` / `WM_VSCROLL` / the wheel / a line typed above / a changed selection / five resizes (the band and the last rows on the window are what a repaint gives: nothing stale).
  the same suite on the build without the band: 30 of its 35 PrintWindow checks go red (the 5 that stay green are the ones that expect a blank band or only check the geometry). the checks of shaped / fallback-font text (arabic, hebrew, thai, devanagari, emoji, and japanese / accents with fewer tries) capture the control's own row again when it differs, up to 8 times: **the control's own row comes out with most of its glyphs missing now and then** (about one run in five, measured with the old build too), the band's row never does.
- **flicker on resize** (asked for on 2026-10-06: "try to make the app not flicker when i resize the window"). **measured first, not reproduced.** `tools\flicker_test.ps1` shows the exe on the real desktop (topmost, never activated, no input sent), resizes it with `SetWindowPos` in small steps and screen-captures patches of the composed desktop in a tight loop (a C# thread: a powershell script block there crashes the host):
  the editor's text (top left, it does not move) and the title text; per frame the number of bright text pixels must not change. **calibrated**: an exe built with `/DFLICKER_PROBE` (an 8 ms sleep between the control's erase and its paint) is caught in 36% of the editor frames and 4% of the title frames, so the harness does see erase-to-paint gaps.
  on the build before these changes: 0 bad frames in the editor and the title over 8 runs / about 1,600 frames today (dark, 300 lines, 500 steps; earlier: light, large steps, 22 lines with the scrollbars coming and going, wrap): nothing to fix there. so only two defensible places were hardened, both can only help:
  `MainProc` answers `WM_ERASEBKGND` without the title strip (the children cover the rest of the client area; the strip is one buffered blit in `FramePaint`: no flat face colour under it first), and `Layout()` moves the menu bar, the editor and the status bar with `BeginDeferWindowPos` / `DeferWindowPos` / `EndDeferWindowPos` (one pass, with `MoveWindow` as the fallback).
  after them (the first build with the band: about 1,600 frames, 1 bad title frame once, none in the next 6 runs). the final exe against the old one, 11 alternating runs of about 200 frames each: the old build had a bad editor frame in 2 runs (2 frames in all), the new one in 4 runs (10 frames in all): too few events to tell noise from a difference, so **no improvement is claimed, and a small worsening was not ruled out** (the band repaint costs 0.2 ms per paint and up to 0.4 ms per `WM_SIZE`; the same build with the band switched off, both instrumented: 1 and 0 bad frames against 1 and 0).
  **what an event log of the resize path showed** (a temporary build with `QueryPerformanceCounter` stamps around `WM_ERASEBKGND`, `WM_PAINT` and `WM_SIZE`, not kept): per resize step the editor gets 2 erases from outside any paint (the system sends them from inside `SetWindowPos`) and one `WM_PAINT` that finishes a median 5.3 ms (p90 7.3, max 31) after them; the paint itself takes 1.4 ms (erase and rows). the erase colour is the editor's own background, so an erase that hits no text is invisible;
  one that hits text would blank it for those 5 ms. **resolved in 1.0.5:** the maintainer confirmed the disappearing editor text, the published 1.0.4 reproduced it, and the editor now answers `WM_ERASEBKGND` with 0 outside a paint (the region stays flagged and the paint erases it; `WM_PRINT` / `WM_PRINTCLIENT` count as paint). See the regression and live-resize results above. The old bitmap attempt flickered because of the control's direct selection painting, so native painting is retained.
  **limits**: statistical (a gap of a millisecond or less is not caught); only the editor's top left and the title text are watched, not the edges (a flash at the right / bottom edge while dragging, in the status bar or in the scrollbars would not show); the status patch is bottom anchored and unreliable (ignored).
  **if it still flickers: say where** (editor text, an edge while dragging, title strip, status bar, scrollbars) and whether it is while dragging an edge, maximizing or toggling the status bar.
- **drag and drop** (`main.c` `OnDropFiles`; `WS_EX_ACCEPTFILES` on the main window, shell32 loaded at run time): files and / or folders dropped on the window put their full paths into the text at the caret (the selection is replaced: `EM_REPLACESEL` = one undo step, then `EM_SCROLLCARET`),
  one per line (CR LF), plain: no quotes, no line break after the last one. the buffer is measured first, so no path is cut (the old 1024 limit is gone). **the drop no longer opens the file** (it used to: the first file in this window, the others in new windows, folders skipped): asked for on 2026-10-06 ("paste the path at the cursor location(s)",
  read as: at the caret, like a paste; there is one caret in the stock edit). **shift held while dropping keeps the old behaviour** (`GetAsyncKeyState`, the real key state: not testable with messages, the code path is the old one). `T24` posts `WM_DROPFILES` with an HDROP built in the test process: the system hands that handle to the app's process.
- **editor padding** (`edit.c` `EditPad`): no frame; the formatting rectangle is the client area shrunk by `EDIT_PAD` (8 px) on the left, right and bottom and by `EDIT_PAD_TOP` (4 px: it was 8 until 2026-10-06, "remove 4px from the top") on the top (`EM_SETRECTNP` replaces the margins, so left / right are in it; `EM_SETMARGINS` keeps them as well).
  **margin, not padding (2026-10-06, "text must go all the way to the edge")**: the control clips its text at that rectangle, so scrolled text used to stop 8 px short of the left edge (and 4 px at the top) and left a blank frame. now with word wrap off the rectangle runs to the right edge of the client area (right to left editors and wrapped text keep the 8 px: nothing scrolls out sideways there), and the strips at the left (rows reaching into it when scrolled sideways), at the top (the end of the row above the first whole one) and below are painted by `BandDraw` / `BandStrip` (the same code and bitmap blit as the partly visible bottom rows; `WM_ERASEBKGND` leaves all three alone). measured: `EM_SETMARGINS` has no effect at all once a rectangle is set.
  the control resets that rectangle to the client area on every size change, so `EditPad` runs after `WM_SIZE` / `WM_SETFONT` too. the scrollbars sit at the outer edges of the editor window (they are the control's non-client area), the padding is inside them.
- **caret**: the stock control's own, an inverting rectangle: pure white on the dark theme's black editor, pure black on the light theme's white one. nothing creates a caret (T19.14 greps the sources for `CreateCaret`).
  (an accent coloured bitmap caret, `AccentCaret` = `(editor background xor accent)`, was used until 2026-10-06 and went back on request.)
- **dirty state by content** (`app_state.c` `g_clean`, `AppMarkClean`, `TextChanged`, `AppIsDirty`): the stock modified flag is sticky, so typing and deleting again, or undoing back to the original, would still ask to save.
  the clean state (what was loaded / saved, or blank for a new document) is kept as length + two 32-bit hashes (no 64-bit math, nothing is copied for a big file); a compare only happens when the control's flag is set and the length is back to the clean one.
  a new encoding / line ending is a change unless the document is empty and unsaved. `AppMarkClean` is called by `OnCreate`, `OpenDoc`, `WriteDoc` and `FileNew` in main.c. the title's `*` and the close prompt both use `AppIsDirty`.
- ctrl+a is an accelerator: in the find dialog it selects inside the focused text box, otherwise in the editor.
- scrollbars only when needed (edit.c `UpdateBars`): a native multiline edit always shows its bars (greyed). we show/hide them with `ShowScrollBar` after text / size / font changes
  (`EditScrollSoon` posts `WM_BARS` so the control finishes its own layout first). pitfalls found the hard way: (1) a hidden bar (WS_xSCROLL cleared) is no longer maintained by the control,
  so its range can't be read -> vertical need = `EM_GETLINECOUNT` vs lines that fit (`EM_GETRECT` / line height); horizontal need = show the bar with redraw off, read `GetScrollInfo`, hide again if unneeded;
  (2) that show/hide resizes the edit -> `WM_SIZE` -> re-schedule = endless posted-message loop that starves `WM_PAINT` (unpainted children) -> `g_inBars` guard; (3) reset scroll position when a bar goes away.
  verified: short doc = none, tall = vertical, wide = horizontal, both, word wrap on (vertical only), typing past the window, window enlarged (bar disappears).
- logical line/col (status bar, goto) = lf count over the edit's own buffer (EM_GETHANDLE + LocalLock), so they stay right with word wrap on.
  goto works with wrap on too (modern notepad behaviour, not the classic "grayed out").
- menus: bar = child window `mp_menubar`; popups = `mp_popup` (WS_EX_NOACTIVATE), private modal loop in `RunMenu` handles mouse/keys/mnemonics/submenus.

  ctrl+(=,+,numpad+) bigger, ctrl+(-,numpad-) smaller, ctrl+(0,numpad0) reset. only translated for messages to the main window, its children and the modeless
  find dialog (so f3 / ctrl+g work from it, like notepad); modal dialogs run their own loop and never see them.

Repeated monitor visits reuse the pair. Chrome font replacements reassign any borrowing help controls before deleting old handles. dialog edits (`UiEdit`) are subclassed for ctrl+backspace (the stock
  edit inserts a DEL character). known gap: a dialog dragged to a monitor with another dpi is not re-laid-out.

- title strip (`frame.c`): the first attempt drew two title bars because the only `WM_NCCALCSIZE` sent by `CreateWindowExW` has `wParam` FALSE (the single-rect form) and nothing recalculated the frame until the first

  verified with `tools\frame_test.ps1` (real mouse input: hit tests, maximize / restore, double click, drag, win+left snap, minimize, close).

  default extension `.txt`, start folder = the current file's folder, else the last folder picked. a native dialog is not ours to theme: **it follows windows' own app mode, not the app theme** (measured on this machine: windows is

## tooling quirks
- RunBash: don't put powershell code in a bash heredoc (gets routed to powershell and breaks). use the Write tool for files.
- `tools\pw_shot.ps1` takes a PrintWindow screenshot on the gui tests' private desktop (`-File -Theme -Cmds -Sel -Text -Out`): nothing shows, no foreground / keyboard / mouse is used, so it is safe while the user works; it cannot show real hover,
  the caret blink or native dialogs. use it first, `shot.ps1` only when the real desktop is needed.
- `tools\probe.bat /DSHOTDC` builds an exe that also answers `WM_APP + 90` (wParam = width, low word of lParam = rows, high word = the first row (0 = the top left corner): dump that part of the editor's own window DC to `%TEMP%\mint_dc.ppm`, a binary ppm; **a pixel read costs about 20 us**, 473,000 pixels outlast the tests' 8 s message timeout: ask for the rows you need)
  and `WM_APP + 91` (blocks found wiped by the control / kept, read-and-clear). it is how to see what a control painted straight onto its window (PrintWindow repaints through `WM_PAINT`; another desktop's DC cannot be read from outside). `/DSHOTDC` code is compiled out of the normal build.
  `T23` and `T25` use it when the exe has it: `ui_test.ps1 -Exe build\probe\notepad-mint.exe -Only T23,T25` (`tools\verify.bat ui` runs both on the probe build).
- `tools\flicker_test.ps1` (batch 7) puts the exe on the REAL desktop for a few seconds (topmost, `SW_SHOWNOACTIVATE`: it takes no focus and sends no input; it does cover whatever is under it), resizes it and screen-captures patches in a C# thread (a powershell script block on a thread crashes the host silently, exit 5). `tools\probe.bat /DFLICKER_PROBE` is its calibration exe (an 8 ms sleep between the editor's erase and its paint).
  a run that is killed leaves `mint_flicker_test.exe` windows behind: kill those by name, nothing else (other powershell processes on this machine are not ours). the status patch of the harness is bottom anchored and races the composed frame: ignore it.
- test scripts: powershell variables are **case-insensitive** (`$n` as a loop variable next to a `[int]$N` parameter = the loop never runs, with no message); wrap long powershell probes in `timeout N`; `PrintWindow` draws the caret: send the editor `WM_KILLFOCUS` (and `WM_SETFOCUS` after) when a compared row may contain it.
  the control's own row via PrintWindow is **flaky for shaped / fallback-font text** (arabic, thai, emoji: now and then most glyphs are missing, also in the build without the band): `Band-Cmp` in `T25` captures it again, up to 8 times, until it equals the band's.
- `cmd.exe /c build.bat` needs the absolute path. screenshots: tools\shot.ps1 (CopyFromScreen of the dwm frame bounds; forces the window to the foreground
  with AttachThreadInput; the keys go to the real foreground window, so runs are flaky if something steals focus).
- `tools\shot.ps1` and `tools\frame_test.ps1` steal the foreground (and the mouse): the user's own typing can land in the test window (it happened: stray text showed up in the editor).
  `tests\ui\ui_test.ps1` does not: it runs the app on a private desktop (`CreateDesktop`) and uses window messages only. `shot.ps1 -Cmd <IDM_ id>` posts a menu command by id; `-Mouse "x,y"` parks the real mouse (hover states),
  `-Burst N` takes N captures in a row (blinking caret), `-Drag "x1,y1,x2,y2" [-DragHold]` drags the real mouse (selection painting). `shot.ps1` kills every running copy of `build\notepad-mint.exe` at the start
  and the end (so close your own notepad mint first); the gui tests run temp copies of the exe, those are left alone (an earlier version killed every "notepad-mint" process, the tests' copies included).
- batch files: the current directory is not on the command lookup path here, so every `cmd /c` / `call` uses an absolute path (`tools\verify.bat` builds one from `%~dp0`);
  `a && b & c` runs `c` unconditionally (use parentheses).
- the unit tests, layout_check, probe builds and the gui suite all write under `build\` (git-ignored) and never touch `build\notepad-mint.exe` except `build.bat` itself.
